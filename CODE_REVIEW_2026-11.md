# Spokium — code review, November 2026

Reviewed on 2026-11-10 at commit `07d411c` (plus the uncommitted 1.5.1 version bump).

Scope: every Swift file in `Spokium/Spokium` (about 5,400 lines), the test target, `scripts/`, the project build settings, and the docs. Ideas listed in `REJECTED_IDEAS.md` and the "out of scope" list in `AGENTS.md` are deliberately not re-proposed.

## How to read this

Each finding has a severity and a confidence.

- **Severity** — High: loses or corrupts what the user dictated, or leaves the mic on. Medium: visibly wrong behaviour or a freeze. Low: rare, cosmetic, or cleanup.
- **Confidence** — *Reproduced*: I ran it. *By reading*: the code path is unambiguous but I did not run the app. *Needs a check*: plausible, needs a manual test.

What I ran:

- A scratch harness that compiles `LiveChunker.swift` unchanged and feeds it synthetic audio (finding 4).
- A read of the app's own unified-log lines for the last 6 days (`Paste result`, `Live chunk queued`, `no speech in the final stretch` — metadata only, no text). 54 pastes, 37 of them multi-chunk sessions. Dev and production share the log subsystem, so both are mixed in.

What I did not do: build the app, run the test suite (it launches the app as test host), or change any code.

## Status (2026-11-10)

Fixed after this review:

- **1** Stop-tail race — queue-idle callbacks ignore the tail; `finishStop()` finishes the session itself when nothing is queued (including the failed-save branch).
- **2** Push-to-record early release — key-up during `.starting` sets `pendingStop`, applied as soon as recording is live.
- **3** Settings device picker — `switchInputDevice` compares against `AudioRecorder.activeDeviceUID` (the device actually in use).
- **4** Whisper chopping — cut placement, gaps and pause length use "not speech **and** not audible"; paragraph breaks in `Transcriber` too. Regression tests added.
- **5** SHA-1 on the main thread — moved to `Task.detached`.
- **6** Stop ignored during a device switch — deferred via `pendingStop`; the resume re-checks the session after each restart and stops the new recorder if it was cancelled.
- **8** Continued session losing its first part — a failed start pastes the pending text (not on explicit cancel).
- **9** Temp file collisions — UUID suffix.
- **10** (part) CFString leak, `TranscriberError` messages, level timer in `.common` run-loop mode.
- **R1** Quit can hang — terminate replies after cleanup or 5 s, whichever comes first.
- Docs: `SECURITY.md` network use, `AGENTS.md` model migration.
- Release hygiene: `scripts/dev.sh` removed (an unchecked copy of `release.sh`); the project is generated by XcodeGen from `Spokium/project.yml`, versions in `Spokium/Version.xcconfig` (no more double build-number bump); tests compile as Swift 6 on 26.3.

Not done yet: A1 (explicit states + controller tests), 7, the rest of 10, R2–R8, P1–P5, latency (L1/L2), release hygiene.

## The short version

The pure-logic parts (chunker, assembler, snippets, device ranking, clipboard restore) are in good shape and well tested. Almost every real bug I found is in the one place with no tests: the recording state machine in `RecordingController`, where `state` plus five side flags (`stopTailTask`, `isResumingAfterSplit`, `pendingStartCancel`, `isLiveSession`, `recorder.isRunning`) encode more states than the enum has.

Fix these first:

| # | Finding | Severity | Confidence |
|---|---|---|---|
| 1 | A chunk finishing during the 300 ms stop tail ends the session early: trailing words are dropped and the whole recording is re-transcribed in the background | High | By reading; near-misses in your logs |
| 2 | Push-to-record: releasing the key before the mic has started leaves the recording running | High | By reading |
| 3 | Changing the input device in Settings mid-recording does nothing | Medium | By reading |
| 4 | Whispered speech is cut mid-word every ~5 s and each piece becomes its own paragraph | Medium | Reproduced |
| 5 | Model SHA-1 check runs on the main thread: several seconds of frozen UI and dead hotkey after each download | Medium | By reading |

After that, the most valuable non-bug work is in "Improvements": a ~0.8 s cut in stop-to-paste time, and making the state machine testable.

## Bugs

### 1. Session finishes during the stop tail (High)

`stop()` sets `state = .finishing` immediately, then waits 300 ms plus the engine teardown before `finishStop()` runs (`RecordingController+Transcription.swift:81-94`). Both `onIdle` closures only check `state == .finishing` (`RecordingController+Live.swift:190-195`, `RecordingController+Transcription.swift:162-165`). So if the last queued chunk finishes transcribing inside that window, `finishSession()` runs while the recorder is still capturing:

1. The text assembled so far is pasted and `endLiveSession` clears `isLiveSession`.
2. `finishStop()` then finds `isLiveSession == false` and takes the file path: it enqueues the **whole segment file** for transcription (`RecordingController+Transcription.swift:118-132`).
3. When that finishes, `state` is `.idle`, so the result is thrown away.

What the user sees:

- Anything said between the last chunk cut and the stop press is missing from the paste.
- A hidden full-length transcription runs afterwards. After a 7-minute dictation that is a long GPU burst, and a dictation started in the meantime queues behind it, so its paste is late for no visible reason.

The same race exists with live mode off, for a continued session (toggle during "Transcribing…", then stop while the first part finishes).

Evidence from your logs: the window is about 0.34 s (the fastest stop-to-paste recorded). It is hit when a chunk was queued roughly 0.4–1.0 s before the stop press. None of the 54 pastes landed in it, so it has not fired this week, but several were close (chunks queued 1.2, 1.5, 1.6, 1.7 s before stop). A paste line with `live=true` and `stop→paste` under 0.30 s is the fingerprint.

To reproduce on demand: temporarily raise `stopTail` to 3 s, dictate 12 s, pause 1 s, say two more words and stop.

Fix: the minimal one is to add `stopTailTask == nil` to both `onIdle` guards. `finishStop()` must then finish the session itself whenever the queue is already empty, because the idle signal it would have waited for has been skipped; the live path does this today (`finishLiveRecording`), the "recording failed to save" branch does not. The better fix is a real `.stopping` state between `.recording` and `.finishing` (see Improvements, A1).

### 2. Push-to-record: early key release is ignored (High)

`handleKeyUp` only acts when `state == .recording` (`RecordingController.swift:167-172`). Key down moves to `.starting`, and the mic takes 100–300 ms to start (1–2 s for Bluetooth). A release during that time is dropped, so the recording keeps running with nobody holding the key. It only ends on the next full press and release, or at the auto-stop limit.

A quick tap, or a short "yes" into AirPods, is enough to trigger it.

Fix: on key-up during `.starting`, set a flag that `startSegment` honours right after `state = .recording` (call `stop()`), the same way `pendingStartCancel` works.

### 3. Settings device picker is a no-op mid-recording (Medium)

`GeneralTab.swift:44-47` calls `controller.switchInputDevice(uid:)` from `.onChange`. By then `@AppStorage` has already written the new UID, so `switchInputDevice` reads the *new* value as `previousUID` (`RecordingController+Segments.swift:140`), decides it is "the same physical device" and skips the split. The recording carries on with the old microphone while the menu and Settings both show the new one.

The menu-bar path works because it calls `switchInputDevice` before anything is written.

Fix: have the controller remember the UID the running recorder was actually started with and compare against that, rather than against the stored setting.

### 4. Whispered speech: mid-word cuts and false paragraph breaks (Medium)

Keep/drop decisions use "Silero speech **or** audible", but cut placement and pause length use the Silero flags alone (`LiveChunker.swift:85-91`, `151-153`, `202-207`). For audio that is audible but scored non-speech, which is what `plan.md` measured for real whispering (Silero max 0.14–0.22), the whole chunk counts as one long "silent tail".

Harness result, 40 s of continuous audio at RMS 0.008 with every window classified non-speech:

```
t= 10.5s  chunk 5.02s  overlap=0.0/0.0  pauseBefore=0.00s
t= 15.5s  chunk 5.02s  overlap=0.0/0.0  pauseBefore=15.02s
t= 20.5s  chunk 5.02s  overlap=0.0/0.0  pauseBefore=15.02s
…
```

So the chunker cuts in the middle of the "silence" every 5 s, with no overlap for the assembler to de-duplicate, and reports a 15 s pause, which becomes a `\n\n` at every seam with the default 4 s threshold. The file-mode path has the paragraph half of this too (`Transcriber.swift:227-229`).

This is the worst case (100% non-speech). Partly detected whispering gets a milder version: cuts in the middle of any whispered stretch of 0.8 s or more.

Fix options, cheapest first:

- Count a window as silent for cutting and for `pauseBefore` only when it is non-speech **and** not loud. Noise then stops blocking pause cuts only where it is above `audibleRMS`, which is the trade-off the comment at `LiveChunker.swift:52-55` chose the other way.
- Or keep cut placement as is, but when the tail being cut is loud, treat it as a forced cut (2 s overlap, word timestamps) and report `pauseBefore = 0`.

Either is a few lines plus a test built from the harness above.

### 5. SHA-1 validation blocks the main thread (Medium)

`performDownload` is main-actor code and calls the synchronous `WhisperModel.validateFile` directly (`ModelManager.swift:452`). Hashing 1.6–3.1 GB there freezes the UI, the HUD and the hotkey for a few seconds at the end of every model download. The Core ML path already does this correctly with `Task.detached` (`ModelManager.swift:299-305`), as does "Verify Hashes".

### 6. Stop is ignored while a device switch is resuming (Medium)

During a split, `state` stays `.recording` but the recorder is stopped. `stop()` returns early on `recorder.isRunning == false` (`RecordingController+Transcription.swift:82`), so a stop press, a push-to-record release or the auto-stop is silently dropped. The retry loop can last up to 11.5 s (`RecordingController+Segments.swift:69`).

Related hole in the same function: after `try await recorder.start(to:)` succeeds, `state = .recording` is set without re-checking (`RecordingController+Segments.swift:84-87`, `105-108`). A Shift+Esc during that await resets the session to idle, and then the resume turns the recording back on, with no Esc monitor and no live session.

Fix: remember a pending stop and honour it when the resume completes, and re-check `state` after each `await` in the loop.

### 7. File mode loads and resamples audio on the main thread (Medium, non-default setting)

`TranscriptionQueue.run` is main-actor and calls `AudioLoader.loadResampled` synchronously (`TranscriptionQueue.swift:148-159`). With "Transcribe while recording" off, a 30-minute recording means reading and converting several hundred MB on the main thread before whisper starts. This compounds the known whole-file-in-memory gap. Moving the load into the `Transcriber` actor (which already has a `transcribe(audioURL:)` overload) fixes the freeze.

### 8. Continued session can lose its first part (Low)

If the user toggles during "Transcribing…" and the new segment fails to start (or is cancelled while starting) after the queue has already drained, `returnFromRecording()` goes straight to `.idle` (`RecordingController.swift:282-289`). The text already assembled for the first part is never pasted. It should call `finishSession()` when there is assembled text.

### 9. Temp file names collide within one second (Low)

`makeTempURL()` uses a second-resolution timestamp (`RecordingController.swift:354-359`). Cancel and restart within the same second gives the new recording the same path, and the cancelled one's async delete (`discardRecorderAsync`) can then unlink the file being written. In file mode that surfaces as "Audio recording failed to save". Add a UUID to the name.

### 10. Small ones

- **CFString leak** — `stringProperty` uses `takeUnretainedValue()` on a value CoreAudio returns retained (`AudioDevices.swift:205-209`). One leaked string per call; `defaultInputName()` runs on every menu open and state change. Use `takeRetainedValue()`.
- **Auto-stop restarts on every segment** — `startSegmentMonitors` re-arms the full limit after each device switch and each continued segment (`RecordingController.swift:312`), so the "30 minutes" limit is per segment, not per recording.
- **Cryptic error text** — `TranscriberError` is not a `LocalizedError`, so a missing or corrupt model shows "The operation couldn't be completed. (Spokium.TranscriberError error 0.)" (`Transcriber.swift:53-57`, `TranscriptionQueue.swift:211`).
- **Selected model deleted in Finder** — `selectedModelURL` returns nil and the app reports "No Whisper Model" even when other models are downloaded (`ModelManager.swift:221-231`). Fall back to any downloaded model. "Verify Hashes" has the same gap after it deletes a failed file (`ModelManager.swift:381-383`), and it also deletes on a read error, not only on a mismatch.
- **Performance stats are skewed** — the timer starts before `await transcriber.transcribe`, so it includes model load on the first run (`TranscriptionQueue.swift:167`). Chunks skipped by the VAD record their audio with near-zero time (`Transcriber.swift:125-129`), which inflates the speed and makes the menu's "~x left" estimate optimistic.
- **Dictionary token budget is overstated in live mode** — the tab shows "/ 224" (`DictionaryTab.swift:50-62`), but the live prompt appends up to 200 characters of previous text after the dictionary, and whisper keeps the *end* of the prompt (`RecordingController+Live.swift:199-208`). A dictionary above roughly 150 tokens loses its first entries without warning.
- **Debug-mode wipe is not immediate** — `UserDefaults.didChangeNotification` is not posted for changes made by another process, so `defaults write … debugMode -bool false` does not trigger the cleanup (`AppDelegate.swift:62-76`). The folder goes at the next in-app defaults write or launch. `README.md:140` says "immediately". KVO on the `debugMode` key works across processes.
- **Shift+Esc gaps** — a global monitor does not see keys sent to Spokium's own windows, so it does nothing while Settings is focused, and key monitoring needs the Accessibility permission, so it never works for copy-only users (`RecordingMonitors.swift:106-117`). A local monitor covers the first; registering Shift+Esc as a hotkey only while a session is active would cover the second.
- **Level timer pauses while the menu is open** — `Timer.scheduledTimer` runs in the default run-loop mode (`RecordingMonitors.swift:54`), so the meter and the dead-mic countdown stall during menu tracking. The queue-status timer already uses `.common`.
- **Stale device list in Settings** — `GeneralTab` loads devices once (`GeneralTab.swift:65-68`); it does not observe `.audioInputDevicesChanged`, so the picker can show a blank selection after a device is unplugged.

## Robustness

**R1. Quit can hang.** `applicationShouldTerminate` waits for `queue.unload()` with no timeout (`AppDelegate.swift:90-96`). A model load or the first Core ML compile (minutes) cannot be aborted, so Quit, logout and restart wait for it. Add a deadline of a few seconds and then reply anyway.

**R2. Live mode has no fallback when the resampler cannot be built.** If `LiveResampler` fails to initialise, the tap runs without it (`AudioRecorder.swift:102`), no samples arrive, and the session ends as "No speech detected" while a perfectly good file is deleted. Fall back to the file path for that session. Worth checking with a multichannel interface in the same pass: the level meter reads channel 0 only (`AudioRecorder.swift:111`), and the mono downmix for more than two channels is up to `AVAudioConverter`.

**R3. Close the audio file explicitly.** The file is closed when the tap closure is released (`AudioRecorder.swift:131-140`). `AVAudioFile.close()` is available on your deployment target; calling it in `teardown()` makes "the file is complete when `stop()` returns" a guarantee instead of a deallocation-order assumption.

**R4. Config changes in the first 2 s are ignored** (`AudioRecorder.swift:223`). That hides the self-inflicted change when a Bluetooth mic wakes, but a real change in that window can leave the engine stopped with only the 5 s dead-mic warning as a cue. After the window, check whether the engine is still running and split if not.

**R5. Download leftovers are never cleaned.** A crash or force-quit between download and validation leaves a `<UUID>.download` of up to 3 GB in the container's temp folder, and an interrupted unzip leaves `.unpack-<UUID>` in the models folder (`ModelManager.swift:323-326`, `510-511`). `cleanStaleTempFiles` only removes `whisper-*.caf` (`AppDelegate.swift:143-151`).

**R6. One `ModelManager`, not ten.** `ModelManager()` is created ad hoc at ten call sites across the controller, the menu and the Settings tab, each with its own copy of `selectedModelName`. Choosing a model from the menu does not update an open Settings window. More importantly, download state lives in the Settings view's `@State`: if SwiftUI tears the view down when the window closes, reopening Settings shows "Download" for a model that is still downloading. *Needs a check*: start a large download, close Settings, reopen. Either way, one app-level instance removes the question.

**R7. The model stays loaded forever.** The whisper context is only freed at quit. For large-v3 that is 3 GB or more of RAM and GPU memory held by an idle menu-bar app; opening the Dictionary tab also loads the full model just to count tokens. Unloading after, say, 15 idle minutes costs nothing in the common case, because warm-up already reloads while the user speaks. The cost is a slower paste for a very short dictation right after a long idle, so it may deserve a setting.

**R8. Sleep and screen lock.** Nothing stops a recording when the Mac sleeps or the screen locks. A recording left on keeps capturing the room until the auto-stop limit, then puts the transcript on the clipboard. Stopping (or cancelling) on `NSWorkspace.willSleepNotification` and on screen lock is a small change that matches the app's privacy posture.

## Privacy and security

**P1. Transcripts reach clipboard managers and Universal Clipboard.** `Paster` writes a plain string to the general pasteboard (`Paster.swift:71-75`). Two consequences sit awkwardly next to "no transcription history on disk" and "no transcription content ever leaves the device":

- Clipboard history tools (Raycast, Maccy, Paste and so on) store every transcript, usually on disk.
- Handoff offers the transcript to the user's other Apple devices.

Both have standard opt-outs: write with `prepareForNewContents(with: .currentHostOnly)`, and add the `org.nspasteboard.TransientType` marker (plus `ConcealedType` if you want password-style treatment). Some users will want transcripts in their clipboard history, so a toggle in Settings → Output is reasonable; I would default it to private.

**P2. Clipboard snapshot reads everything eagerly.** `ClipboardRestorer.snapshot` pulls the data for every type of every item on the main thread (`ClipboardRestorer.swift:69-73`). With a large image or a copied file on the clipboard this can be slow, and it forces apps that provide data lazily to render every format. Consider a size cap above which the restore is skipped.

**P3. Device names are logged as public.** Bluetooth device names often contain a person's name ("…'s AirPods"); they are logged with `privacy: .public` (`AudioRecorder.swift:201`, `RecordingController+Segments.swift:134`). Not transcript content, but easy to make private.

**P4. Model downloads follow `main`.** The URLs resolve against the moving `main` ref (`ModelManager.swift:23`, `36`). If upstream ever replaces a file, every download fails its hash check until an app update. Pinning the Hugging Face commit in the URL makes downloads reproducible. Separately, the models are checked with SHA-1 while the Core ML encoders use SHA-256; Hugging Face publishes SHA-256 for both.

**P5. The DELETE at quit may not be sent.** `cleanup()` calls `roomQuieter.end()`, which fires a detached request, and the app exits shortly after (`RecordingController.swift:175`, `RoomQuieter.swift:40-54`). The device's own 30 s timeout covers it, so this is a note, not a problem.

## Improvements

### Latency: stop-to-paste

Your logs give a baseline: median 1.18 s from stop to paste, range 0.34–2.60 s. The 0.34 s floor is the stop tail plus engine teardown; the rest is transcribing the final chunk after the stop.

**L1. Transcribe the tail speculatively.** When the queue is idle and the current buffer ends in a pause of about 0.8 s, start transcribing a snapshot of it without cutting. On stop, if no speech arrived after the snapshot, use that result as the final chunk. If speech continued, discard it (abort via the existing epoch when a real chunk arrives). Chunk boundaries and accuracy are unchanged, which is what parked the "earlier pause cuts" idea in `plan.md`; the only cost is some extra GPU work. For the common "finish, breathe, press stop" pattern this removes the whole post-stop transcription, taking the median to roughly 0.35 s.

**L2. Skip the stop tail when the user has already gone quiet.** The tail exists for people who stop the instant they finish a word. If the live sink already shows half a second or more of trailing silence, the last word has clearly ended and the 300 ms wait buys nothing.

Together these would put most pastes at about 0.1 s after the key press. Fix bug 1 first: both ideas touch the same code.

### Architecture

**A1. Make the session state explicit and testable.** This is the highest-leverage change in the review. Bugs 1, 2, 6 and 8 are all interleavings the current flags do not rule out, and none can be unit-tested today because `RecordingController` constructs its own recorder, queue and paster.

- Add the missing states to the enum: `.stopping` (tail and teardown in progress) and a "switching device" sub-state of recording. The UI can keep mapping them to the existing HUD modes.
- Put the recorder, queue, paste and clock behind small protocols, as `APP_REVIEW_IDEAS.md` already proposes, and write table-driven tests for the orderings: chunk completes during the tail, key-up during starting, cancel during resume, stop during resume, start failure in a continued session.

**A2. Give the Transcriber its own executor.** `transcribe` is a synchronous actor method, so each whisper run blocks a thread of Swift's shared concurrency pool for its whole duration. It works, but giving the actor its own serial-queue executor is the supported way to host long blocking work and removes any chance of starving other async code.

**A3. Do not write the native-rate file in live mode unless something will read it.** Live sessions still record a CAF at the device's native format (about 23 MB per minute for 48 kHz stereo), used only by debug mode and the planned retry. When retry (D5 in `plan.md`) lands, keeping the 16 kHz mono stream instead would be about 4 MB per minute and would not need resampling again.

### Tests

- **T1.** State-machine tests, as in A1.
- **T2.** A regression test for finding 4, taken from the harness (a classifier that returns all-false over audible samples).
- **T3.** An inference smoke test with no checked-in audio: synthesise a sentence with the system speech synthesiser at test time, run it through `Transcriber` with the tiny model, and skip when the model is not in the dev container. Today nothing exercises whisper itself, which `plan.md` already lists as unverified after the 1.9.5 bump.
- **T4.** The test target builds in Swift 5 mode with a 26.5 deployment target, while the app is Swift 6 on 26.3 (`project.pbxproj:302`, `310`). Aligning them brings strict-concurrency checking to the tests.

### Release and repo

- **Tag releases.** The only tags are `v1.3.2` and `v1.4.0`. `dist/1.5.1` was built from a tree whose version bump is still uncommitted, so there is no commit that corresponds exactly to the shipped 1.5.1. `release.sh` could refuse a dirty tree, then commit the bump and tag at the end.
- **Keep dSYMs per release.** `release.sh` deletes `build/` at the start of each run, taking the previous archive with it. `dist/1.5.1` has dSYMs (copied by hand, it seems) and `dist/1.5.0` does not; without them a crash report from that version cannot be symbolicated.
- **`dev.sh` is `release.sh` minus the checks.** It notarises and installs to `/Applications` without running tests or `check.sh`. One script with a flag would stop them drifting apart.
- **The xcframework carries six unused slices.** iOS, tvOS and visionOS variants are tracked alongside the macOS one: about 67 MB of the 82 MB of tracked framework files. Building only the macOS slice shrinks every future framework bump in Git.
- **No update path.** Users on GitHub Releases never learn about new versions. An auto-updater would break the no-network rule, but a "Check for Updates…" menu item that opens the releases page in the browser makes no request from the app.
- **Log subsystem is hard-coded** to `com.spokium.mac` in eight places (one file uses the bundle ID instead), so dev and production logs are indistinguishable. A shared constant derived from the bundle ID fixes both.

### Feature ideas

None of these overlap the rejected list; each is a product decision rather than a recommendation.

- **Retry for failed chunks** — already D5 in `plan.md`. Worth noting that today a failed live chunk leaves a silent hole in the pasted text; the alert is the only cue.
- **Transcribe an audio file** — a "Transcribe File…" menu item reuses the whole pipeline. It needs the user-selected-file read entitlement, so it changes the entitlement table.
- **Beam search as an accuracy option** — the app uses greedy sampling. With chunks capped at 30 s, beam search may be affordable on recent chips. Worth an A/B behind a hidden default using debug-mode recordings before deciding anything.
- **Insert text without the clipboard** — setting the focused element's selected text through the Accessibility API would avoid the save-and-restore dance entirely where it works, with ⌘V as the fallback. I am not sure the sandbox allows this; it needs a short spike before it is worth discussing.

## Quick manual checks

Things reading could not settle:

1. With Settings focused, press ⌘, — does a second Settings window open? Both `SpokiumApp` and `AppDelegate.settingsScene` declare a `Settings` scene.
2. Start a large model download, close Settings, reopen it — is the progress still there? (R6)
3. Does the HUD appear over a full-screen app? The panel's collection behaviour has `.canJoinAllSpaces` but not `.fullScreenAuxiliary` (`RecordingOverlay.swift:41`).
4. With sounds on, record nothing and stop. The start sound plays after the engine starts, so the mic hears it; check a debug sidecar to see whether it ever reaches whisper as "audible" content.
